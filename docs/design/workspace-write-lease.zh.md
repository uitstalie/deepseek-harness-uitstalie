# 工作区写租约

[English](workspace-write-lease.md) | 中文

状态：已实现——一个 checkout 一把写租约、`WORKSPACE_LEASE_HELD` 与 `WORKSPACE_LEASE_LOST`、空闲过期与最大生存时间、回收、fencing 与审计日志都随工作区工具集交付。可选的排队、界面徽标与子代理继承租约尚未实现。篇幅上限：10 页 / 4,600 汉字；本稿约 3,940 汉字（约 7 页）。

## 1. 背景与事故

两个 dev 会话在同一时间写同一个 checkout。用户亲眼看到两个会话在同一目录里改文件、跑 `pwsh`，彼此都可能覆盖对方的成果。会话日志在 turn 821 记录了这个时刻：两个会话都各有一个 `pwsh` 作业在同一 dev checkout 里执行，当时唯一的应急办法是停掉其中一个，让另一个继续。同一次事故也留下了一条决定：中止第二个会话来停止并发写，并把“工作区写租约”列为后续任务。

根因是结构性的，不是模型犯错。一个工作区就是一个目录；任意多个会话都能打开它；harness 里没有任何东西把它们的写操作串行化。git、构建产物、`node_modules`、生成文件、部署脚本都默认只有一个写者。两个写者可以在没有任何工具报错的情况下丢数据。

本文定义一个租约，把“单写者”假设显式化并可执行。它不改变权限模型：有写权限的会话仍然可以写，但只能在持有工作区租约时写。

## 2. 范围、目标与非目标

### 2.1 目标

1. 一次只有一个写者：在第一次写类工具调用前获取租约；租约被占用时给出明确的持有者报告。
2. 冲突不静默继续。失败的会话收到带类型的错误，写明持有者、获取时间与当前操作。
3. 崩溃可清理：死会话或宿主重启留下的租约在有限时间内被回收；被回收后的旧持有者不能再写。
4. 可见与可审计：界面能看到当前写者；每次获取、释放、冲突、过期、回收都有记录。

### 2.2 非目标

- 不做按文件加锁，不做文件内部的合并或冲突解决。
- 不改沙箱或权限策略；租约与它们正交。
- 不防护 DSH 之外的进程（编辑器、终端、CI）对同一 checkout 的写入。
- 默认不排队；排队是可选模式。
- 不做跨工作区原子事务；会话只写自己的工作区。
- 不给读者做快照隔离；租约串行化写者，不串行化读者。
- 不保留 JIRA 兼容：JIRA 已废弃，按停用处理，其账本在 checkout 之外，不属于租约。

## 3. 粒度：一个 checkout 一把租约

租约按会话工作区的规范项目根做键：一个 checkout 目录一把租约。

为什么这个粒度够用：

- 真正会出事的冲突都在 checkout 层：git 索引与引用、构建产物、生成文件、lockfile、部署脚本，都是该目录所有写者共享的。
- 按会话加锁在“会话与会话冲突”时没有意义；按文件加锁覆盖不了 shell 命令、构建和部署这类一次动很多文件的操作。
- 每个 checkout 一个资源，足够简单，能推理、能展示、能审计。

盲区也写清楚：

- 两个不同的 checkout、worktree、clone 互不阻塞。对源码写入这是对的，但它们仍可能在租约之外的共享包缓存或共享部署目标上互相影响。
- 只读操作永不获取租约。两个读者可以在写者工作时运行，也可能看到写了一半的目录树；租约不提供快照隔离。
- DSH 之外的进程可以在不询问的情况下写同一 checkout。租约是 DSH 会话之间的约定，不是目录的文件系统锁。
- 会话写自己工作区之外的路径不在本租约覆盖内；那由沙箱与权限策略兜底。

## 4. 什么算写入

### 4.1 分类

每个工具声明一个租约类：`write`、`read` 或 `exempt`。未知工具默认 `write`，因为漏判写入正是本设计要防的故障。

| 类别 | 工具与操作 |
|---|---|
| `write` | 文件写入、编辑、打补丁、创建、删除、移动、复制；`pwsh` 与任何 shell/终端工具默认写入；git 写命令（`commit`、`add`、`checkout`、`merge`、`rebase`、`reset`、`push`）；构建；部署；包管理安装或更新；`tool-dsh-store` 的创建与删除；任何在 checkout 下创建或修改文件的工具 |
| `read` | `read`、`glob`、`grep`；会话搜索、事件读取、trace；记忆检索与读取；`workspace_sessions`、`workspace_tasks` 读取、`workspace_message` 读取、`workspace_artifacts` 列出与解析；`tool-dsh-store` 查询 |
| `exempt` | 控制面状态，必须在 worker 持有租约时仍可写：`memory_write` 写记忆存储、`workspace_tasks` 的任务与回执写入、`workspace_message` 的消息日志写入、租约与审计文件。这些写入有版本守卫或是追加式，不是源码变更 |

### 4.2 shell 命令

shell 工具什么都能跑，所以安全默认是 `write`。初始只读白名单就是这六条：`git status`、`git diff`、`git log`、`ls`、`pwd`、`rg`。只有在命令是单个可执行文件、没有管道、重定向、命令替换或串联时，才按 `read` 处理；其他情况，包括任何复合命令，都要获取租约。往白名单加命令需要评审。

白名单是便利，不是安全边界。被标成 `read` 的 shell 命令如果实际写了文件，那是分类 bug；第 1 阶段（只观察）就是用来在强制之前找出这些 bug 的。

### 4.3 新工具

新工具必须声明 `leaseClass`。注册的工具没有分类时构建失败；启动审计会把未分类工具按 `write` 列出并告警。这样分类是“构造上穷尽”的，而不是靠评审者记得每个工具。

## 5. 获取与冲突行为

### 5.1 何时获取

租约在会话对它的工作区第一次调用 `write` 类工具时、工具执行之前获取。它按会话持有，不是按一次调用或一个 turn 持有，这样多轮编辑不会每一步都重新获取。

顺序是：先过权限与策略检查（被拒绝的调用不获取租约），再获取租约，再执行工具。`read` 或 `exempt` 调用永不获取。

### 5.2 冲突

如果租约被另一个活着的会话持有，调用以带类型的错误失败：

```
WORKSPACE_LEASE_HELD
workspace:  D:\dqc\deepseek-harness-uitstalie-dev
holder:     { sessionId, title, acquiredAt, lastOperation, expiresAt }
```

错误写明持有者、何时获取、在做什么、租约何时过期。失败的会话不继续、不静默重试、不写入。它向用户报告冲突，或询问怎么办。持有者的 `sessionId` 可以链接到另一个会话去查看。

### 5.3 排队

默认关闭排队，因为两个会话互相等待正是租约要防的故障。

启用后，获取是 FIFO，带超时与取消：等待者收到位置，可被 turn 取消，超时后收到 `WORKSPACE_LEASE_TIMEOUT` 与持有者报告。超时的等待者永不继续。队列长度有上限；队列满时立即拒绝，而不是继续增长。

## 6. 释放、续期、过期与崩溃恢复

### 6.1 正常释放

会话被销毁、会话结束、或持有者显式释放时，租约释放。释放删除租约记录并追加一条审计。崩溃导致的未释放由下面的过期处理。

### 6.2 续期与最大生存时间

持有者在每次 `write` 工具调用时续期，并有心跳。租约有两个边界：

- 空闲过期，例如十分钟没有写入或心跳，避免被遗忘的会话永远占着 checkout；
- 最大生存时间，例如八小时，即使一直在续期也过期。超过最大时间的构建必须重新获取，这是“把上限调高”的信号，不是无限持有。

续期很便宜：更新租约记录里的 `expiresAt` 与心跳时间。阻塞执行器的长命令不会阻塞心跳定时器。

### 6.3 崩溃、取消与宿主重启

租约记录放在 checkout 之外：`$DSH_HOME/workspaces/<规范根哈希>/lease.json`，获取是原子的（先建锁目录，再写记录）。记录里有工作区路径、持有者会话 id 与标题、获取与过期时间、最后操作、主机 id、进程 id、fencing 代数。

- 宿主启动时扫描租约目录。主机与进程都已消失、或已过期的租约被回收，并写审计。
- 进程还活着但会话已不存在的租约，在空闲过期后回收，而不是立即回收，避免切断一个慢工具调用。
- 持有者还活着但租约已过期的，被回收；持有者的下一次写入因 fencing 代数过期而收到 `WORKSPACE_LEASE_LOST`。这种拒绝只在回收方仍活跃时持续：一旦该记录被删除、过期或它的进程死亡，被隔离的写者会回收租约并继续（见下面的 fencing）。

### 6.4 fencing

每次获取与回收都会递增租约记录里的 fencing 代数。持有者保存自己获取到的代数。每次写入前，守卫重读租约并比较；不一致说明租约已被回收，在新持有者仍活跃时写入被拒绝。这防止旧持有者在新持有者获取之后继续写。恢复不是抢占：当前记录不存在、租约已过期或进程已死亡时，被隔离的持有者下一次写入会以代数 `(current?.generation ?? mine.generation) + 1` 回收租约，追加 `reclaimed` 与 `acquired`，更新自己保存的代数并继续。仍活跃的别的持有者依旧以 `WORKSPACE_LEASE_LOST` 拒绝。observe 模式永不拒绝：同样回收陈旧记录，或在新持有者仍活跃时不让调用重写记录而直接继续。

残留缺口是：租约被回收时已经在跑的 shell 命令仍然能写，因为操作系统进程没有被停掉。设计通过“最大生存时间大于任何预期命令”、记录回收、告警新持有者来限制它；杀掉旧进程不在范围内。

### 6.5 无死锁论证

论证很短，可以直接检查：

- 每个 checkout 一个资源。
- 一个会话最多持有一把租约，且只为自己工作区获取；它不会在持有租约时等待第二个工作区。
- 获取默认非阻塞。可选的队列是 FIFO 且带超时，等待者不可能永远等。
- 租约总能被持有者释放，否则会过期并被回收。

因此等待图无环：会话要么持有唯一租约，要么带超时地等待它；没有会话在持有一把租约的同时等待另一把。若将来允许跨工作区写入，必须按规范路径顺序获取，失败时一起释放；同样的无环顺序仍成立。

## 7. 可见性与审计

### 7.1 界面可见性

宿主暴露只读的租约状态，例如 `lease.current({ workspace })`，返回持有者、获取时间、最后操作、过期时间。会话列表在该 checkout 上显示写入徽标与当前持有者标题。错误与徽标用同一份持有者报告，模型与用户看到的是同一组事实。

### 7.2 审计日志

每个事件向 `$DSH_HOME/logs/workspace-lease.jsonl` 追加一行 JSON：

```
{ ts, event, workspace, sessionId, title, operation, result, holder?, generation }
```

`event` 取 `acquired`、`denied`、`released`、`expired`、`reclaimed` 或 `lost`。`operation` 记录工具名与目标路径，不记录完整命令，避免把 shell 行里的凭据抄进日志。日志按天轮转，保留 30 天；轮转前有大小上限。

审计日志是追加式，不是工作区内容，所以它永远不需要租约。它也是第 1 阶段冲突报告的数据来源。

## 8. 与现有机制的关系

### 8.1 子代理与 fork

子代理跑在父会话的会话树里、同一工作区，它继承父会话的租约，而不是再获取一把。fork 是有自己身份的新会话，不继承租约。如果父会话持有租约，fork 的第一次写入会被拒绝并给出持有者报告，这对一个可能写入的分支正是预期行为。

### 8.2 调度批处理

每个调度任务作为自己的会话运行。如果一批任务指向同一个 checkout，任务会串行：第一个获取，其余被拒；如果批处理启用了队列，则排队。批处理里的只读任务不获取租约，可以并发。想要吞吐的批处理应按 checkout 拆分任务。

### 8.3 只读分析

只读分析永不获取租约。它可以在写者工作时运行；结果可能过期或看到写了一半的树，这对分析是可接受的。如果分析需要一致快照，它应等待或请写者释放，而不是拿租约。

### 8.4 权限

租约不授予也不拒绝权限。没有写权限的会话先被现有策略拒绝，轮不到租约；有写权限的会话仍然需要租约。两种失败不同：`WORKSPACE_LEASE_HELD` 是冲突，不是权限错误，不能当成权限错误报告。

## 9. 测试

| 测试 | 通过条件 |
|---|---|
| 两个会话、同一 checkout、都写 | 一个获取；另一个收到 `WORKSPACE_LEASE_HELD` 与持有者；失败者没有写任何文件 |
| 启用队列，第二个等待 | 第一个释放后第二个获取；超时返回 `WORKSPACE_LEASE_TIMEOUT`，第二个永不写入 |
| 写者持有时两个读者 | 两个读者都成功；都没有获取租约 |
| 持有者崩溃 | 过期后新会话回收；审计有 `reclaimed`；旧会话下次写入在新持有者活跃时收到 `WORKSPACE_LEASE_LOST`，之后该持有者释放、过期或死亡时，旧会话以 `reclaimed` + `acquired` 恢复，记录不存在时代数为 `mine + 1`，过期/死亡时为记录代数 `+ 1` |
| 宿主重启 | 启动扫描回收陈旧租约；新会话可以获取 |
| 子代理写入 | 继承父会话租约；没有第二次获取 |
| 父会话持有时 fork 写入 | 被拒，并给出持有者报告 |
| 未分类工具 | 构建或启动检查失败；该工具按 `write` 处理 |
| shell 只读白名单 | `git status` 不获取；`git commit` 获取；带管道或重定向的命令获取 |
| 审计 | 每个事件一行 JSON，字段齐全；不出现完整命令文本 |

## 10. 上线与风险

### 10.1 阶段

| 阶段 | 做什么 | 验收 | 回滚 |
|---|---|---|---|
| 1. 观察 | 给所有工具分类；计算并记录“本会被拦”的冲突；界面显示“would be blocked”徽标；不阻断 | 事故模式出现在审计里；行为不变 | 关掉功能；无数据要撤销 |
| 2. 强制 | 用 `WORKSPACE_LEASE_HELD` 阻断；默认不排队；启用回收与 fencing | 两会话测试、崩溃测试、只读测试通过；审计可用 | 切回观察模式 |
| 3. 队列与界面 | 可选 FIFO 队列与超时；持有者徽标与状态面 | 队列测试与界面状态通过；没有卡死的等待者 | 关闭队列；强制保留 |

第 1 阶段是在会话被阻断之前找出分类错误的稳妥方式。观察满 2 周或累计记录 20 次“本会被拦”的冲突后，才进第 2 阶段强制互斥，以先到者为准。第 2 阶段才是真正修事故。第 3 阶段是便利。

### 10.2 风险

- **分类漏判**：写工具或 shell 命令被标成读。缓解：默认 `write`，每个工具必须声明类别，用第 1 阶段找漏。
- **误判**：长构建把另一个会话阻塞几小时。缓解：持有者报告、文档化的释放方式、空闲过期；最大生存时间兜住最坏情况。
- **回收后的陈旧租约**：在跑的命令仍能写。缓解：对新调用 fencing、最大生存时间大于预期命令、审计告警；杀旧进程不在范围内。
- **跨进程竞争**：两个宿主指向同一 checkout。缓解：租约记录放在 checkout 之外且获取原子；不支持没有原子创建的网络文件系统。
- **审计泄漏**：命令可能含凭据。缓解：只记工具名与目标路径，永不记完整命令。
- **用户困惑**：被阻塞的会话看起来像坏了。缓解：错误写明持有者，界面有徽标，提示词让模型报告冲突而不是重试。

## 11. 与另外两份设计的冲突

| 点 | 另一份设计说 | 本设计说 | 以哪份为准 |
|---|---|---|---|
| 控制面写入 | `workspace_tasks` 与 `workspace_message` 写 `.dsh` 下的日志 | 这些写入是 `exempt`，worker 持锁时仍必须可写 | 本设计定租约类别；工作区设计定工具归属 |
| `workspace_artifacts` 发布 | 为已有文件发布引用 | 发布只做索引；创建新文件仍要 `write` 工具与租约 | 本设计定租约类别 |
| `superagent_*` 控制写入 | 工具面设计把它们迁到 `workspace_*` | 它们的日志写入是 `exempt`；改源码的动作跟随新工具的类别 | 本设计定租约类别；工具面设计定迁移 |
| 只读分析 | 两份设计都不要求读拿锁 | 读永不获取租约 | 无冲突 |
| 工具分类 | 另外两份设计定工具归属与命名 | 本设计定每个工具的租约类别，不论归属 | 本设计赢在租约类别；另外两份赢在归属 |

JIRA 已废弃：不保留兼容层，其账本在 checkout 之外，因此不构成冲突。其余各行按表内结论处理。

本文不修改记忆/工作区设计与工具面设计。工具在归属之间移动时，它的租约类别跟着走；移动不改变加锁规则。
