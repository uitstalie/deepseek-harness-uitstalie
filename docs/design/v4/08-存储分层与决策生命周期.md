# 08 存储分层与决策生命周期

来源：2026-11-28 讨论。起因是两个问题——workspace 信息现在怎么存的；推理/决策怎么衰减、几天后回来的用户怎么接上。中途以 analyze 工作区（大量"一单题一会话"）为反例校准了粒度。

## 1. 现状：workspace 信息分五层（实测）

| 层 | 位置 | 形态 | 存什么 |
|---|---|---|---|
| ① 注册表 | `~\.dsh\storages\workspace.json` | 单 JSON（19 KB） | 工作区 id/路径/标题/`role`；全部已归档会话 id 平铺数组 |
| ② 工作区状态目录 | `~\.dsh\workspaces\<ws-id>\` | 每工作区一目录 | `sessions\*.json`（成员关系，233–400 B）、`tasks\*.json`（任务全文+receipts，2–5 KB）、`messages\*.json`（逐条投递+回执）、`dispatches\*.json`（投递关系）、`lease.json`（写租约） |
| ③ 旧派发账 | `~\.dsh\storages\superagent.sqlite` | SQLite，一表 680 行 key→JSON | 退役超控派发记录，**自带 `outcome` 和 `decisions[]` 字段** |
| ④ 会话本体 | `~\.dsh\sessions\<路径编码>\session-*.v4.jsonl.zstd` | 事件流 zstd | 对话与执行痕迹（推理在这里） |
| ⑤ 投影缓存 | `~\.dsh\storages\session_projcache\sessions\*.json` | 每会话一 JSON | tokenUsage、contextPressure、contextBreakdown 等折算值 |

结构性发现：

- **没有"汇聚态"层。** ② 的每条记录都是事件态（一条任务/消息/投递/成员关系）。"这个工作区进行到哪了"只能遍历 tasks+sessions 在内存里拼——这就是 super 每次 probe 的原因。
- **旧账比新账字段更好。** sqlite 旧账（2026-11-06 起）每行带 `outcome` + `decisions[]`（例："APK 已拉出并核对… 上一轮 ROW/a154bf3f 实为旧版"——决策行的活样本）；新的 `workspace_tasks` 反而没有 decisions 字段，判断只能塞 note。**这是字段退化，迁移时应把 decisions 加回 task 记录**。
- 两套派发账并存（sqlite 旧账 + workspace tasks），设计上要收敛为一套。

## 2. 目标布局：统一到 `~\.dsh\workspace\`

```
~\.dsh\workspace\
  registry.json            # 索引：id → 路径/标题/role/档位（现 workspace.json 退化而来）
  <ws-id>\
    tasks\                 # 任务全文 + receipts（现 workspaces\<id>\tasks）
    decisions\             # 决策账（新）：追加型，一行一决策
    state\                 # 两级状态卡（新）：workspace.md + cases\<单号>.md
    messages\ dispatches\  # 投递与回执（现状保留）
  sessions\                # 或维持会话本体在原位，注册表只存指针
```

- 这是**搬家不是重构**：会话日志、投影缓存机制不动；注册表从"含全部归档会话 id 的平铺数组"退化为纯索引。
- 迁移注意：`role` 现在存于 workspace.json（04），档位化后这里改存"档位名"；sqlite 旧账只读保留或导出为 decisions 的历史种子。

## 3. 决策与推理的生命周期：三层温度模型

| 层 | 放什么 | 放哪 | 可达性 |
|---|---|---|---|
| 热 | 完整轮次（含推理） | 当前会话 surface | 直接在上下文里，可卸载（01/02） |
| 温 | 决策行：时间/诉求/判断（含否决）/目标/结果 + **指针**（sessionId+seq 范围+task id） | 工作区决策账（`decisions\`） | 随时可查，**常驻不过期** |
| 冷 | 会话日志原文（推理还在） | session.v4.jsonl.zstd | 只能显式装载，按指针走 |

核心转念：**推理不需要"存了再过期"——日志 append-only，压缩不删；过期的是"快速可达性"。**

- TTL 建议：任务闭环后 N 天（或会话归档）后，访问层不再自动提供推理，只呈现决策行。N 是策略参数，不是机制。
- "遗忘几天后回来"的路径：读决策账（未闭环行常驻）→ 看到指向 → 需要细节才装载冷层。热层丢了不丢事实，因为事实（决策）在温层。
- 递进/step 关系住在账本里：决策行按 task/案件号串链，不在推理里。回看链条 = 读账，不需要重放推理。

### 3.1 冷层回读：验证结果（2026-11-28，推翻"没有通道"的判断）

四件事都查了，结论是**通道存在，但都不是一等公民**：

| 路径 | 状态 | 限制 |
|---|---|---|
| `session-query-sqlite` 服务 | 已挂载，`openAt: never` | 全文搜索关闭（报 `SESSION_QUERY_SEARCH_DISABLED`）；**精确读取、标题、血缘追踪仍可用**（base `cordis.patch.yml:161-166`） |
| `dsh-tool-session-query`（5 个模型只读工具：`session_event_read` 等） | **未挂载**（本机 profile、四个 preset 都没有这行） | 挂载是一行配置；但授权按 `cwd` 严格相等——super（`D:\dqc\superAgent`）读不了 dev 工作区的会话，只能读自己 cwd 的 |
| Web `/export` 与复制 Markdown | 已挂载（`dsh-session-log-export`） | 人工路径，模型不可用 |
| 直接读 `session.v4.jsonl.zstd` | 机制上可行 | 帧扫描 + 单帧解压已验证（本会话 13,025 帧，任意中间帧可单独解压）；但这是**文件访问**，不是 API，没有授权约束——任何有 fs/shell 的 agent 都能读任何会话日志 |

所以"按指针装载冷层"在**自己会话**内可以做（挂工具），**跨工作区**则没有受支持的路径：要么扩展 `tool-session-query` 的授权（按 workspace 注册表判权，而不是 cwd），要么在 workspace-tools 里加一个"读某会话某段 seq"的动作。文件直读是兜底，但它是绕过授权面的，不能当设计依据——否则任何子代理都能翻别人的日志。

另外，"日志永不删"要收一收：压缩与归档都不删，但用户 `delete` 会删；冷层不是绝对存在。

## 4. analyze 反例：缺的是"案件"层

现状：一单题一会话，但"单"没有显式化——没有 task 绑定、没有闭环回执，工作区呈现为一堆平铺会话，乱。

结论：设计不动摇，补粒度——**状态卡两级**：

- 工作区级 = **开放案件索引**：每案一行（单号/状态/承办会话指针/下一步），几行到十几行；
- 案件级 = 单案状态卡（02 判断 8 的结构），挂在 task 上。

派发纪律：**一单 = 一 task（targetSessionId 指承办会话）= 一会话**。analyze 的乱正是 07 时序图缺 task 绑定时自然长成的样子；反过来说明图上的"send actors"一步不能省 task 记录。

## 5. 对既有文档的修订

- **决策账不能放在可变的 task 记录里**（推翻原稿）：task JSON 的 status/receipts 会被改写，`decisions[]` 放进去就不是 append-only，回放和审计都不成立。改为：**决策行写 append-only 事件流**（会话日志的 `decision/recorded` 事件，或工作区级 append-only 文件），task JSON 只存**决策引用**（decision id 列表）；`decisions\` 目录是索引，不是真源。sqlite 旧账的 `outcome/decisions[]` 作为历史种子导入，字段形态对齐决策行五要素。
- **温层常驻规则对齐 02**：常驻 = 未闭环行 + 最近 N 条闭环行（N 为策略参数）；更早的闭环行只在档案里，按需检索。原稿"决策账常驻不过期"作废。
- **TTL 要有执行者**：不设常驻进程；由访问层在"读账/派发"两个时机判定——超过 N 天的推理指针降级为"只列决策行，不自动装载推理"。判定发生在读取时，不是后台任务。
- **注册表搬家是持久化迁移**：`storages\workspace.json` 是带版本号的持久化单元（`unit: workspace, version 2` + `global.workspaceIds` + 全部归档会话 id），workspace-tools 按该路径读。迁移要带版本升级、双写窗口与回滚，不是挪文件。
- 03"决策账放在哪"→ 收敛为本页结论；02 判断 8（状态卡）→ 细化为两级（工作区索引 + 案件卡）；02 判断 6 → 补"最近 N 条闭环"。

## 6. 未决

1. TTL 的 N 与降级点：读账时降级，还是写入时就只留指针（后者更简单，但丢"三天内可回看推理"的便利）。
2. 跨工作区冷层回读的授权方案：扩展 `tool-session-query` 按 workspace 注册表判权，还是 workspace-tools 加读动作。文件直读只能兜底，不能当通道。
3. 决策事件的归属：写进执行会话的日志（谁做谁记），还是写进工作区级 append-only 账（谁派谁记）。倾向后者——super 派发时就能写，不依赖 executor 自觉。
4. `sessions\` 是否物理搬进 `~\.dsh\workspace\`——不动也行，注册表存指针即可；搬家收益低、风险高。
