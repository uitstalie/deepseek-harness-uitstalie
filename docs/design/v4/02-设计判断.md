# 02 设计判断

按讨论顺序记，先结论后理由。每条都能在 01 或 04 里找到对应数字或代码。

## 一、Super Agent 的上下文怎么切

1. **它的"工作区信息"= 用户诉求 + 判断 + 派发目标。** 推理是生产这三样的过程，出了结果就能压成一句话。"工作区信息最便宜"说的是单位，"推理占 38.4%"说的是体积，两者不矛盾。
2. **压缩单位：一行一次决策。**
   ```
   时间 / 用户诉求（原话或一句转述）/ 判断（含否掉了哪条路）/ 派给哪个工作区哪个会话哪个任务 / 结果状态
   ```
3. **零决策的轮次整段可删。** 查文件、跑命令、看日志这类没产生决策的回合，天然可卸。
4. **决策行在派发那一刻写，不等压缩。** 等压缩时推理已经没了，还得回头重读日志，多花一次。
5. **判断必须留否掉的选项。** 只写"派给 dev"、不写"为什么不自己改"，下一个会话会重走老路；重复查询 14% 就是证据。
6. **读回分两级**：常驻"未闭环的行"；闭环行是档案，按需读。这样常驻上下文 ≈ 系统提示 + 角色工具集 + 未闭环账本 + 最近几轮对话。
7. **决策账是会话外的文件，不是 memory。** memory 只收全局事实，业务状态进不去。

## 二、工作区会话：从复用转向新建

8. **可以转向"一任务一会话"**，前提是一张工作区状态卡：
   - 当前任务
   - 已定结论（带理由）
   - 未决问题
   - 试过且失败的路径（最贵，别丢）
   - 关键文件指针
   - 下一步
   - 目标 1–2k token，不是日记。
9. **状态卡写入时机**：开工读一次；里程碑写一次（会话可能被打断，不能只在收工写）；收工写一次，并在 task receipt 里引用版本。
10. **状态卡载体是工作区文件**（如 `.dsh/state/current.md`），不进 memory；更新校验挂在 task receipt 上，否则三周后烂掉。
11. **转向新建会话要先改复用规则**：`prompt.ts:68` 现在明写"派发前先复用会话"，工具的派发顺序（先 list/get 再 run）也是复用优先。规则和工具要一起改，否则打架。
12. **两个粒度是同一机制**：super agent 记决策账，工作区会话记状态卡；都要在动作发生时写，不能等压缩。
13. **温层常驻规则（与 08 对齐）**：常驻 = 未闭环行 + 最近 N 条闭环行；更早的闭环行只在档案里，按需检索。推理指针随行保存，超过 N 天降级为"只列决策行、不自动装载推理"，降级判定发生在读取时。
14. **决策账是 append-only，不能塞进可变的 task 记录**：task JSON 存决策引用，账本本身写事件流或工作区级追加文件（08 §5）。

## 三、Role 的位置

- Role 是切口，但切的是**工具面**（占预占 75%），不是消息。
- 消息层更细的轴是 `source.kind`（`user` / `agent-instructions` / `skill-catalog` / `time-context` / `runtime-context` / `compact-checkpoint`），压缩与 prune 都按 seq 段走，不看来源。
- 现在没有任何工具声明 `minRole: 'super'`；agent 级工具约 2,700 token，subagent 看不到。
- "任务 ↔ 上下文段"的绑定不存在：任务板（Agent Teams）有 owner 和 blockedBy，但不携带任何上下文引用。
- **设计按"角色档位"建，不按 `super` 写死**（2026-11-28 定）：super 只是第一个档位实例。将来 role 可能通过其他途径确定（工作区配置、preset 绑定、派发链路推导），所以装载/卸载规则、决策账、状态卡都挂在档位配置上——一张可加行的映射表（角色 → 工具面 → 注入 → 保留策略 → 账本格式），不是散在各处的分支。role 本身怎么确定是开放问题，见 03。
