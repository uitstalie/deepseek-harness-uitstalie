# 07 目标工作流：超级节点时序

来源：2026-11-28 时序图（角色 → super agent → actors → reviewer）。这是目标形态的第一次具体化：**super agent 是超级节点，人只操作超级节点，图上的其余节点由它控制**。图不是线性流程——run、recheck、ask question 都可以循环，实际是一个带超级节点的图。

## 时序与机制的对应

| 图上的步骤 | 对应机制（见 04） | 对应设计（见 02/03） |
|---|---|---|
| 角色 → super agent：send an action | 用户消息进 super 会话 | 常驻保留（2.1% 那部分，不卸） |
| find proper workspace | `workspace_sessions.list`（世界快照） | 常驻"未闭环账本"消掉大部分这类查询 |
| read workspace info | `workspace_sessions.get` / `workspace_tasks.get` | **按需装载**，打 `load:ws-<id>` 标，引用结束卸载 |
| re-translate user requests to actors | super 的判断过程 | **决策行在此刻写**（判断含否掉的选项），推理本身之后可卸 |
| send actors | `workspace_tasks.create` + `workspace_sessions.run` | 决策行闭环的前半（派发目标）落账 |
| actors: do actions | 子会话执行，一任务一会话 | spawn 用精简子档位（06）；fork 接续才继承 |
| reply action | task receipt / `workspace_message.send` | 状态卡更新校验挂 receipt（03 第 5 条） |
| need special review → send review request | **reviewer 是第四类档位**：只读核查档位 | 档位映射表加一行；reviewer 收派发权、只给读 + 报告 |
| reviewer: reply to | reviewer 报告回 super | reviewer 报告本身也可按决策行压缩 |
| super → 角色：reply to user | 回复 + 决策行闭环 | 闭环行归档案，未闭环行常驻 |

## 循环（图上没画全的部分）

- **多轮 run**：super 派发 → 回执不合格 → 补任务再派。收敛靠 receipt 的 acceptance 核对，不能无限跑。
- **recheck**：super 复核 actors 的产出。低成本形态是"要 receipt 摘要 + 抽查文件"，不是重新执行。
- **ask question**：actors 或 reviewer 把问题发回 super（`workspace_message`，super 是唯一对人窗口）。问题本身也是决策行的一种：问了什么、怎么答的。
- **循环边界**：每条派发链要有预算（轮次/费用/时间），到线必须回人。这是"不做自提升工作流"在图上的落点——超级节点控制循环，人控制超级节点。

## 图没画但必须有的

1. **状态卡写入点**：actors 收工时写工作区状态卡，图上没有这步，没有它"每次新建会话"就是空转。
2. **reviewer 的独立性**：reviewer 不能是 actors 自己（自查无效），要独立档位、独立会话；`writeScopes` 提示可以用于防利益冲突，但它只是提示（04）。
3. **决策账的归属**：图上每个箭头都对应账本里的一行或一段；超级节点的账本 = 它对这张图的全部长期记忆（02 判断 6）。

## 超级节点的职责边界（从图推出的）

- **控制的是图，不是内容**：super 不替 actors 干活，它找节点、翻译诉求、派发、核对、升级审查。落到上下文上：它保留判断与派发记录，卸载执行痕迹——和 02 的切法完全一致。
- **图可以长**：actors 不止一个、reviewer 可以多级（recheck 循环就是隐含的二级图）。但超级节点只有一个，人是唯一能操作它的一方。
- **将来形态**：这张图 + 决策账 + 档位映射表，就是"精细上下文 v4"的运行时图景。设计收敛后，07 这张对应表是验收基准：图上每个箭头都能指到机制和档位。
