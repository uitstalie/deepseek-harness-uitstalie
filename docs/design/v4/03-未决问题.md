# 03 未决问题与下一步

## 设计前必须过的六件事

1. **provider 接不接受"删旧 thinking、旧 tool input 换成摘要/空对象"。** wire 上 `tool_use.input` 可以给 `{}`，thinking 块也可以不带签名，但模型行为会不会变没测过。这决定第一刀能不能切在推理上。
2. **中间 prune 一次的真实缓存代价。** 按当前约 78k 的会话，估计一次要重发 20–60k token，没实测。这决定卸载是"随手做"还是"攒到自然断点"。
3. **保留策略按什么分。** 按类别（推理/参数/结果）还是按任务（`task-<n>` 绑定）？后者要新造"任务 ↔ 上下文段"字段，现在没有。
4. **工具面按角色/预设怎么分组。** super 现在 45–47 个工具全装；到底需要哪些，没列过。
5. **状态卡的更新校验怎么挂到 task receipt**：谁核对、什么时机、版本怎么引用。
6. **决策账放在哪**：super 会话自己的文件，还是各工作区 task 记录汇总成一张账。——2026-11-28 收敛（见 08 §5）：账本 append-only，写工作区级追加事件流；task JSON 只存决策引用；`decisions\` 是索引不是真源。剩余问题变成"决策事件写在执行会话还是工作区账"（08 §6 第 3 条）。

## 角色的开放性（2026-11-28 补）

现在只设计 super agent，但 role 将来不排除通过其他方式确定（按工作区配置声明、按 preset 绑定、按派发链路推导，都可能）。所以：

- **设计里不写死 `super` 这个词**。装载/卸载规则、决策账、状态卡都挂在一个抽象的"角色档位"上：每个档位是一份配置——工具面、注入集合、保留策略、决策账格式。super 是第一个实例，不是唯一值。
- **role 的确定途径留成开放问题**（现状见 04）：现在只有 `agent.options.role` 声明和 workspace 注册表一个持久点；preset 绑定、会话头声明、动态指派都还没做，也不在本次范围。
- **映射表要可加行，也要可改行、可减行**：现在复用的词表只有 DSH 自带的三个 `super` / `agent` / `subagent`（`agentRoleOf` 写死这三个值），后面不排除调整。所以设计的落点不在 role 的**词**上，而在**档位**上——档位是配置条目，role 只是档位的一个索引键。将来词表变化（拆分 super、合并 agent、改名、引入新档位如 organizer / specialist）时，改的是映射表和索引，决策行、状态卡、账本结构不动。
- **排序假设也要可弃**：现在的 `subagent < agent < super` 是等级排序（`ROLE_RANK`，`core/tools/src/role.ts:14-19`），工具门 `minRole` 靠它比较。档位化之后，"谁比谁大"不再是天然事实——比较逻辑要跟着映射表走，或者换成显式的能力集合，不再假设线性等级。这是词表调整时最容易漏的一处。
- **决策行和状态卡的"作者"字段按 role 记**，不按会话记：换实现（比如将来 super 的活分给别的角色）时，账本结构不用动。

## 档位的承载物：agent preset 就是现成的 role（2026-11-28 定）

**判断：agent preset 与"角色档位"的要求几乎一一对上，role 应落在 preset 上，不必发明新机制。**

| 档位要求 | preset 现状 |
|---|---|
| 一份配置打包（工具面 / 注入 / 提示段） | `PresetDefinition` = id + 一列 Cordis 插件行（`agent-preset-registry/src/definition.ts:5-11`），工具、命令、技能 provider、提示段全是插件的产物 |
| 同 preset 共享稳定前缀 | preset 决定工具 schema 与提示段，Lead 与 fork 子级同 preset 时请求前缀一致（tool-agent-team README 的 KV Cache 论证同构） |
| 声明式、可加行 | preset 就是声明式 YAML 插件行列表；加一个 role = 加一个 preset 目录 |
| 会话内绑定留痕 | `agent-preset/selected` 事件 + `agentPreset` 投影（`session.ts:36-46`），恢复/fork 重建同一份 |

**已知边界（不是缺陷，是设计选择，要用就得接受）**：

1. **切换只许空白会话**：`select()` 对 `lastTurn > 0` 抛 `agent-preset/locked`（`index.ts:367-369`）。理由：preset 决定模型可见的工具与提示，中途换会破坏"模型可见 ⟺ 已记录"。也就是说 preset 是**开档时定档，运行中不换**——中途能换的只有单维（权限、沙箱、模型、工具增删、plan、Team）。
2. **bundle 只有 cordis / standard 两个**（本机 12 个会话的头部统计），需要按 role 加档位就是加 preset 定义。
3. **role 与 preset 现在是两条平行线**：`agentRoleOf` 三个硬编码值管 `minRole` 工具门；preset 管 组合。落档位到 preset 后，`minRole` 三值词表要么退役（工具门改为"档位配置里声明装载哪些工具"），要么保留作粗筛。倾向前者——工具面归 preset，role 词表只剩语义标签。
4. **中途切档没有批量接口**：单维切换各走各的事件，存在"半个档位"中间态。当前设计选择"开档定档、不中途换"，此问题不存在；若将来要中途换档，需要 plan 模式式的 pending 协调（多维度挂起、下一 step 边界一次生效），列为将来问题，不进本次。
5. **子代理档位：继承是默认，精简是优化项**（2026-11-28 判断）。不写子 preset 就继承父档位，功能上零配置可跑；但两个代价随派发频次放大——① 子代理全额背负父档位工具税（cordis 继承 = 每个子代理首轮 15,058 token 的 45 个工具，精简子档位可压到约 7–8k）；② 继承给子代理完整派发权（`workspace_sessions` / `subagent` 均 `minRole: 'subagent'`，子代理可再派代理、查所有工作区）。规则：fork 接续父工作的继承；spawn 独立任务用精简子档位（收窄工具面、不装派发类工具）；需要独立组合的专家写专属 preset 走 `allowedAgentPresets` 白名单（模型侧选档开关已现成：白名单配置 + `agent_preset` 参数，`tool-subagent/src/preset-selection.ts`；本机 cordis 未配白名单，现全部继承）。
