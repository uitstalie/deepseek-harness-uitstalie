# 本 session 任务方向纠正记录（2026-11-13）

> 用途：作为 dev 侧 personality 插件的**预备输入**——记录用户在本 session 内对任务方向的纠正，以及每次纠正的根因。
>
> 范围：只记**方向性纠正**（怎么做事、范围、表达形态）；不记内容事实纠正（如"暗码是设计如此""OCR 是 4167"），那类属于业务知识，进 KB 而非 personality。
>
> 计数：**13 次方向纠正**（另有若干内容纠正，见文末"不计入"）。

## 一、逐次记录

### 1. 只列清单，不要直接行动
- **原话**：「不要着急，先列出来，而不是直接行动」
- **我做错**：拿到反馈后直接改 KB，边改边报。
- **期望**：先出清单供审阅，得到"落地"指令再动。
- **根因**：把"推进速度"当成价值，把审阅当成阻力。

### 2. 把"忽略"当成"改规则"
- **原话**：「我说的意思是忽略未实现的这种反馈，不是让你改！」
- **我做错**：把"这类不考虑"理解成"从文档里删掉这个方向类别"，还加了一节"已否掉的提案"。
- **期望**：这类反馈不纳入分析范围、不进清单、也不变成任何规则。
- **根因**：把"用户的排除指令"翻译成"文档需要修改"。

### 3. 自造抽象结构
- **原话**：「我从来没说这是映射表」
- **我做错**：造出"映射表"，要求用户确认"第 N 条对应哪张单"。
- **期望**：按用户看到的条目顺序逐条对应即可。
- **根因**：面对不确定时，倾向造一个中间结构来表达，而不是直说"顺序对不上"。

### 4. 自造代号
- **原话**：「这份提案没有意义，单子是谁，失败原因是啥都没有……全都是自己编的不知所云的代号」
- **我做错**：用 `P1–P22`、`C1–C10` 编号组织文档。
- **期望**：单号、文档标题、人话。
- **根因**：为了压缩表达引入内部 ID，忽略了文档是给人看的。

### 5. 自作限制
- **原话**：「谁说只改三处的，不排除重写」
- **我做错**：按"最小改动"给方案，把重写排除在外。
- **期望**：先判该改还是该重写，成本不参与决策。
- **根因**：默认"改得少=风险低"，把自己的成本偏好当成用户的口径。

### 6. 跨文档关系：在"搬运"和"引用"之间摇摆
- **原话一**：「skills 又不知道 007 文档的内容，agent 读完 skills 之后不是直接蒙圈了？」
- **原话二**：「文档之间的引用应该是引用序号或者标题，而不是连内容都混合在一起写」
- **我做错**：先要求 skill"内容自足"并把 014 的内容搬进 skill，随后又整体删除。
- **期望**：只经 `doc_id《标题》` 或检索词关联；skill 只需告诉"查哪篇、查什么"。
- **根因**：把"读得懂"与"背下来"混为一谈；摘要也是第二份内容，同样会漂。

### 7. 擅自扩大范围（一）
- **原话**：「先处理反馈，你管那些干啥」
- **我做错**：反馈之外主动提议"去摸 skill 副本/部署面"。
- **期望**：只做当前明确任务。
- **根因**：把"未来隐患"当成"当前任务"。

### 8. 擅自扩大范围（二）
- **原话**：「dev 停，我说的就是其他之前审查过的插件」
- **我做错**：让它枚举 `docs/reviews/` 全量找问题。
- **期望**：只针对已审查过的那几份报告/插件。
- **根因**：用"全仓普查"替代"按点名范围推导"。

### 9. 默认维持现状（不一致时不作为）
- **原话**：「那的更新生产啊，怎么能不一致呢，不一致搞什么！」
- **我做错**：发现包/生产不一致后，倾向"先不动生产，等确认"。
- **期望**：目标是消除不一致，不是保留现状。
- **根因**：把"谨慎"当默认，把"一致"当成可选项。

### 10. 把决定权上推
- **原话**：「MR非要我合并嘛，你自己合并得了」
- **我做错**：每次合入都请示。
- **期望**：授权范围内自行合并（CI 绿、无冲突、目标分支明确）。
- **根因**：把"需要用户确认"当成安全默认，忽略了这会让用户当执行器。

### 11. 把"汇总"当二次加工
- **原话**：「文档汇总就是原文的统一集合，不是真的让他汇总，打断他」
- **我做错**：安排它写导航索引/职责表/变更史。
- **期望**：把原文原样拼在一起，能一口气读完。
- **根因**：把"整理"理解为"解读"。

### 12. 把不可判定的事写成规则
- **原话**：「未实现这种不考虑，因为你不知道对方会不会实现，什么时候实现，实现出来是啥，这情况无法处理」
- **我做错**：把"未实现"设成一个分析方向。
- **期望**：不可判定的状态不进方向表，只能写"待验证"。
- **根因**：希望"覆盖所有情况"，忽略了"覆盖"会制造假结论。

### 13. 简化判定逻辑
- **原话**：「第 7 条逻辑被简化了……按照 lssi 的分析逻辑来说，确定自研 app 有问题，或者 app 和系统错配就可以了，建议是 clone 给 lssi」
- **我做错**：把"自研预置应用"简化成"必须落到具体 app，别推给三方"。
- **期望**：结论只需到"app 本身有问题"或"app 与系统错配"，**不替 LSSI 裁定该改系统还是改 app**。
- **根因**：把"要把问题定位清楚"误解成"要给出责任分工"。

### 14. 漏项：没做对象对账
- **原话**：「super agent，memory 的审查报告呢？」
- **我做错**：处理多插件整改时，只按手头几条推进，漏了 memory 那份已存在的审查报告。
- **期望**：先把"已审对象"列全，逐个对账。
- **根因**：没有把"多个来源"显式列成清单。

## 三、给 personality 插件的输入（可直接转成约束）

1. **范围**：只做用户本次点名的对象与其直接推导；额外风险最多一行提示，不展开成任务。
2. **先后**：涉及文档/规则/KB 内容变更时，**先出清单**，等"落地"再动。
3. **表达**：面向人的产出禁止自造代号；引用一律单号或 `doc_id《标题》`；不引入用户没用的术语。
4. **不改写用户原话的含义**："别管/不考虑/忽略" = 从范围剔除，**不是**去改文档。
5. **授权内自决**：已有明确授权（如 MR 合并）不再逐次请示；只在改变授权边界时问。
6. **判据只写到能证明的层级**：不可判定的状态只能"待验证"；不替对方裁定内部分工。
7. **一致性优先**：发现两份东西不一致时，默认目标是消除不一致，不是保留现状。
8. **多来源任务先清点**：把"已审对象/已改对象/未改对象"列全再动手。

## 五、用户的表达习惯与用词特点

> 这一节是**解读输入**：同一个意思他常只说半句，personality 插件需要把"原话形态 → 真实意图"对上。

### 5.1 句式结构

| 习惯 | 例子 | 含义/处理 |
|---|---|---|
| **`<角色>：<指令>`** 前缀 | 「img：可以，做吧」「dev：提交修复」「analyze：D:\dqc\xxx.7z」 | 前半指定**执行方**（工作区），后半才是任务；不要当成普通句子读 |
| **「先…而不是…」** | 「先列出来，而不是直接行动」 | 纠正**做法顺序**，不是否定目标 |
| **「不是让你…」** | 「不是让你改！」 | 我做了他没让做的事；意图是**收缩范围**，不是全盘否定 |
| **「就是…」** | 「场景汇总就是原文的统一集合」 | 下定义、收窄口径；后面跟的才是唯一解释 |
| **反问表肯定** | 「配置文件错了不是系统问题嘛？」 | 这不是提问，是**已有结论的通知**；要按结论改，不要反过来解释 |
| **警告式反问** | 「怎么能不一致呢，不一致搞什么！」 | 强烈要求**消除状态**，情绪词只是强调 |
| **「我说了…」** | 「我说了我要重新看文本」 | 我已表达过但没被执行；先补，不要辩解 |
| **编号逐条裁决** | 1…14 每条一句话，判断与处置同句 | 每条独立生效；「drop」「不管」即终态，不要再列"暂缓" |

### 5.2 高频词与口头禅（含默认语义）

| 词 | 语义 |
|---|---|
| **drop / 算了 / 不管 / 不要了** | 终止处理，从范围剔除；**不要**再归档、再列待议 |
| **先…再…** | 明确顺序，顺序错了即使做对也算错 |
| **顺便 / 顺便再** | 同一轮追加，不另起任务 |
| **拿出来我看看** | 要**原文**，不要摘要、不要解读 |
| **没必要 / 没有意义 / 不需要** | 不要做；不要给替代方案论证 |
| **可以，做吧** | 授权，且**不要再确认** |
| **别 / 不要** | 硬约束，无例外 |
| **嘛 / 得了 / 服了 / 咋** | 语气词；表示"这事显然/别再折腾"，不改变指令内容 |
| **那的…啊** | 方言化口语（如「那的更新生产啊」= 那就去更新生产），语义按前后文正推 |

### 5.3 用词特点

1. **中英混用**：`skill / MR / KB / log / app / clone / drop / REA / OCR / RC` 直接用，不加引号，视为通用词。
2. **省略主语宾语**：「清理掉，不要了」「加上备注」「让他跑吧」——对象靠上文；**不要反问"清理什么"**，先按上下文取最近的候选，做之前用一行确认即可。
3. **括号补充条件**：「（注意方向走不通的时候可以换相近的方向）」——括号里通常是**重要约束**，不是旁注。
4. **口语压缩**：「都不挨着」= 逻辑不连贯；「这什么玩意」= 内容无价值/不可用；「蒙圈」= 读者无法执行。
5. **对时间与因果敏感**：「等 ingest 完了之后」「等这一波反馈处理掉之后」——**前一动作完成是后一动作的前置**，不许并行。

### 5.4 对 agent 的称呼与路由习惯

- 用「**img / dev / analyze / super agent**」直呼工作区或角色，后面接任务；出现「super agent」时通常是在**考我全局职责**（例如"memory 的审查报告呢"）。
- 一般**不解释背景**，默认我已知道上下文；因此遇到指代不明，应回显一句"我理解为 X"，而不是停下来问一串。
- 纠错时**只指出错在哪**，不重述正确做法；复述正确做法是我的责任。

### 5.5 给插件的解读规则（原话 → 动作）

```
"先…"          → 重排顺序，别急着产出
"不是…"        → 收缩到被否定的那一块之外
"就是…"        → 以他给的定义为唯一口径
"算了/drop"    → 删除并停止记录，不留待议
"拿原文"       → 给原始内容，禁止二次加工
"可以，做吧"   → 执行，不再确认
```

## 六、一句话总结

他纠正的从来不是"你懂得少"，而是"**你多做/快做/替我决定/替我表达**"——13 次里有 5 次属越界。personality 插件最该约束的不是知识面，而是**动手前的边界与产出形态**。
