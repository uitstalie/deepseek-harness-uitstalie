# Independent review of the Windows super agent evaluation (k3.1)

English | [中文](windows-superagent-eval-k3.1-review-2026-11-09.zh.md)


Date: 2026-11-09. Review subjects: the [Windows on-machine evaluation report](windows-superagent-eval-2026-11-09.md) and its [handoff document](windows-superagent-eval-handoff-2026-11-09.md). This review only read the original report, source code, configuration, logs, and databases; it did not modify the original report, production code, or configuration, and made no commit or push. The independent race rerun created only the synthetic journal `.tmp-eval/journal-race-k31-review/`; after it failed to complete, it was terminated and the directory was deleted.

## 1. Review conclusion

**Partially accepted. The C+ rating and the four P0 findings listed in the original report are accepted, with four P0 findings retained and none downgraded; the conclusion that the dispatch domain was “not opened/all traffic used Markdown” is not accepted, nor is the downgrade of default memory search to P2.** The C+ rating’s statement that “the normal path works, but completeness, failure recovery, and lifecycle closure are not complete” is consistent with the evidence. It does not require lowering the rating to C, nor does it support raising it to B.

The four P0 findings have different levels of evidence: automatic `returned` for empty output has a complete live causal chain; cross-process claim has a reasonable synthetic experiment and deterministic source-code evidence, but the original stdout was not retained and this review has not independently reproduced 26/6; delivery failure and abort are deterministic code defects and should not be labeled as reproduced on Windows. Not inducing the latter two failures on the machine reduces “on-machine evidence coverage,” not the severity of these deterministic defects.

The three evidence issues that most need priority correction are:

1. The SQLite WAL already contained same-day writes before the report cutoff. The domain finding is factually incorrect and should be withdrawn rather than retained at a lower severity.
2. “Historical EPERM was not reproduced” can apply only to this review’s ACL probes. The same machine already had build evidence at 02:22 of `Access is denied` for an esbuild temporary file, and the writer, token, and root cause remain undetermined.
3. 26/6 lacks raw race logs and true two-Host end-to-end delivery evidence. The “remount recovery” unit test only invokes the turn-end handler directly and cannot prove startup recovery.

### P0-1 measurement basis

The report’s `26/6` algorithmically means “six unique pending ids should each have been claimed successfully once, but the child processes actually obtained 26 non-empty claims,” not “26 duplicate deliveries.” Nor is it a count of journal corruption; `0 corrupted rows` means only that the appended text is parseable, not that state transitions are legal. The 3000 seed ids, 12 child processes, and three rounds do not cover crashes, settle, recipient deduplication, or real Cordis Hosts, so they cannot be extrapolated to a live failure rate.

### P0-3 recovery semantics

Failure can be a persistent, visible business state, but it must have an explicit retry or controlled automatic recovery; `failed` must not mean that no further operation is possible. Startup recovery also must not unconditionally treat every pending item as “just completed”: it should reconstruct reportable results from persistent turn/end and requestId. If a crash occurs after a successful queue but before settle, file locks alone cannot provide end-to-end exactly-once; a stable report identity, recipient idempotence, or explicit at-least-once semantics is also required.

## 3. Version and terminology issues

### 3.1 Version boundaries are basically sound

The HEAD of both runtime `D:\dqc\deepseek-harness-uitstalie` and dev was verified as `2026-11-09 权限修复基线`; PID 5084 was still started at 09:45:03 with `node --import tsx/esm apps/cli/src/bin.ts web`, and the runtime worktree had zero status entries. Source-code judgments should therefore use the clean runtime tree, and must not cite dev’s 73 uncommitted tracked changes as loaded behavior. The original report clearly states this limitation.

The same HEAD still does not mean that all runtime conditions are identical: the profile, optional-service mount timing, process token, log cutoff, and continuously changing journal/SQLite must each be fixed separately. This review read the actual `web/cordis.patch.yml`, the base bundle’s storage routes, and live Inspect; the `storageDomain` service and the `include:storage-domain`/`include:jira-agent` entries were all present. The profile’s current mtime is later than the start time, so the existing configuration alone cannot prove every field’s original value at startup; it must be considered together with the bundle and live behavior.

### 3.2 Fedora, the old runtime, and current Windows are not systematically conflated

Section 5 of the original report explicitly treats Fedora’s “never reports back” as old-runtime history and uses the current Windows journal as counterevidence; it does not directly treat Fedora figures as Windows figures. “Overturning the old conclusion” should be limited to: **the observed happy path on the current Windows runtime reports back automatically, and the old runtime’s general report-loss conclusion can no longer be applied.** This does not prove that every normal, restart, or multi-Host path is reliable.

The original cutoff’s 10 delivered/10 task-report can be verified; at review time, the journal had grown to 14 ids with 12 delivered/2 pending, and the super log also had 12 corresponding same-day `[task-report]` entries. The sample consists of that day’s existing real tasks rather than random sampling. It is sufficient to establish that automatic reporting capability exists, but has clear selection limits: one Host, a bound superSession, no injected failures, no abort, no restart, and one no-text diagnostic report. It cannot support the stronger conclusions that “10/10 means the loop is complete” or that “there can be no sample bias.”

### 3.3 Memory severity is inconsistent with the supplied scale

The original report lists unavailable default `memory_search` as P2, but `goal/memory-plugin-assessment-2026-11-08.md:138-144` explicitly lists the same issue as **P1**, and the handoff document also lists unavailable default search as P1. P1 should be restored according to that scale; `memory_read` not distinguishing interrupted/failed can remain P2. Section 6 of the memory report lists several repair recommendations as P0, which does not mean that this Windows round reproduced those failures; new on-machine P0 findings should not be added without retesting. Consecutive-turn summary coverage, stale-maintenance coverage, and checkpoint partial commits are current source-code issues/existing recommendations. This report should at least list them as unverified gaps rather than silently omitting them.

## 4. Accuracy of the Windows-specific observations

### 4.1 Dispatch domain: the original conclusion is factually incorrect and P1-1 should be withdrawn

The current read-only SQL query shows that `u_superagent_dispatch_dispatches` has **89** rows with statuses **62 returned / 23 pending / 4 failed**, the latest `dispatchedAt=2026-11-09T02:26:14Z`, and **14** same-day rows. More importantly, the same-day rows predate the report being written to disk: `task-mw8lnutt` was created at 01:45:59 and returned at 01:50:57, `task-mw8lxomm` returned at 02:02:01, and `task-mw8m5yg4` changed to failed at 02:12:52 in synchronization with the manual resolve. These are not changes that appeared only after this review.

The main database mtime remains 09:31:48, but the WAL is already about 247 KB and continues to update. **In WAL mode, looking only at the main database mtime misses committed writes.** The original report’s earlier observation of a 0 B WAL cannot negate the same-day records already present in the same database.

`superagent_ledger list` returning tasks that exist in Markdown does not prove that they are “Markdown-only.” `dispatch-store.ts:179-187,204-227` migrates Markdown and synchronizes projections; the durable query at `:234-249` naturally returns the same tasks. The original report did not label the data source of the seq 863 result and did not first query whether that id was already in SQLite, so the premise of the inference “list returns ⇒ store.list undefined ⇒ table undefined” is invalid. P0-2’s final SQLite failed matches super seq 911-912 exactly, which instead proves that at least that manual resolve used the domain.

The conclusion should be: **the current runtime’s domain is open and used by dispatch/resolve; withdraw the findings and “near-P0” wording that say “never opened,” “Markdown throughout,” “zero today,” and “75 rows.”** The single sampling of `ctx.get('storageDomain')` during construction at `dispatch-store.ts:169-171` remains a static late-arriving-service risk, but is not the root cause in this on-machine review. A separate P2 can cover “tools do not expose the domain/Markdown source and downgrade reason”; if the product requires a single permanent authority, assess the need for P1 separately.

### 4.2 ACL and Low: the current state is accurate, but attribution and historical relationships need rewriting

Read-only `icacls` verification confirms that the `deepseek-harness-uitstalie-dev`, `superAgent`, and `system_img` roots all have `Everyone:(CI)(DENY)(S,DC)` and `Low Mandatory Level:(OI)(CI)(NW)`; `analyze` does not have that DENY and is Medium. This matches the original report’s current-state table. This review did not recreate the inheritance probes, so it adds no independent proof that “all new files are Low.”

The handoff’s “cleaned up” has contemporaneous records from 11-07: ledger `:4023-4069` states that DENY was removed from 15 paths and nine directories changed from Low to Medium at that time, and ordinary-permission operations were verified in seven worktrees; `:4075-4083` further records that code no longer writes Low/DENY and the old backend is disabled by default and fail-closed. **Successful cleanup at that time and Low+DENY appearing again on the three current roots can both be true; the handoff should not simply be called fabricated or said never to have cleaned up.** ACEs have no timestamps, so the current state cannot distinguish incomplete cleanup, a later rewrite by an old process, or reapplication when this workspace was opened; `analyze` being Medium also does not prove that “not opened” is the sole cause.

P1-2 can therefore remain as “persistent ACL/integrity side effects currently remain or have reappeared, with the writer and time undetermined,” but its title should not state outright that “the Windows sandbox still changes ACLs.” Proving attribution requires controlled before-and-after snapshots, actual write logs, or filesystem auditing, not merely correlation across three roots.

### 4.3 EPERM: failure to reproduce with a probe does not mean this round had no permission failure

`.tmp-eval/acl-probe.mjs` covers only root-file write/rename/unlink, root-directory mkdir/rename/rm, and one child-file write. Even if all these operations succeeded at the time, that shows only that this token, path, and operation set produced no error. The report’s statement that “Deny DeleteChild does not take effect” is too absolute: inheritance flags, the parent directory’s DELETE_CHILD, the target’s DELETE, directory-versus-file differences, and restricted tokens each require separate verification. FullControl on the root object cannot explain every deletion path.

The same machine’s ledger `:6294-6312,6396-6397` already recorded a repository-wide build result of 9/10 at 02:22, with `Access is denied` while the Web phase deleted `%TEMP%\esbuild-*`; three retries, a TEMP change, and a minimal reproduction without Vite still failed. This happened before the evaluation report was written at 10:25, but §3.5 abbreviated it to “historical EPERM was not reproduced this round,” an important omission of scope. It should read:

> This ACL root-directory probe did not reproduce the historical rename EPERM; on the same day, Web/esbuild temporary-file deletion produced Access denied and an ordinary build did not pass. The two error types have different process tokens, paths, and root causes. They cannot prove or disprove each other, nor can they both be attributed to Low/DENY without evidence.

A separate P1 environmental investigation is recommended for this build permission failure. This review’s independent race command also observed esbuild `spawn EPERM`, but that supports only “permission restrictions exist in the current execution environment”; it does not determine the root cause of the esbuild deletion failure or identify the sandbox writer.

## 5. Omissions and overstatements

### 5.1 Lifecycle risks that should be added

1. **Settle failure leaves delivering behind**: `superagent.ts:3716-3733` records a journal settle write failure only as a warning. If delivery actually occurred but delivered was not persisted, a later resend may occur after the lease expires; startup still does not scan. This is a static extension of P0-3, not a new on-machine failure.
2. **Archive/stop races with delivering**: `dispatch-reports.ts:271-279` handles only pending; `:4570-4607` does not wait for in-flight deliver/settle, so a late send may still occur after archiving. The original report’s “reclaim after lease expiry” is incomplete.
3. **Abort and accepted=false**: `:3157-3168` writes `resumed:true` without checking `admitted.accepted`; ordinary append/prompt can also leave a pending binding after accepted=false. This belongs in P0-4 acceptance, rather than checking only whether prompt was called.
4. **Recipient fallback**: `:3670-3703` selects the most recently updated super root Session when superSession is empty, which may not be the original dispatcher. Today’s reports all have explicit recipients, so this is only a static risk; the goal already lists it under the P0 lifecycle, and it should remain a P0-4 related item.
5. **Module-level journal owner and quiescence**: `reportJournals` at `:836-851` is a module-level Map, and dispose at `:4985-5004` neither clears the Map nor waits for report processing that has already started. List this as a separate static risk under the Cordis lifecycle, and add deterministic tests that no late send or write occurs after dispose.

These additions do not change the count of “four original P0 findings retained”; they extend the evidence for existing P0-3/P0-4. Whether to add separate entries can be decided after independent reproduction.

### 5.2 Other conclusions that need correction or narrower limits

- **Missing domain authority**: withdraw this; see §4.1. Do not continue to treat UI/Remote “necessarily seeing state from two days ago” as an on-machine impact.
- **Visibility in P2-4 and P0-3**: writing failures only to the host logger is a core recovery gap, not merely low-priority observability polish. P0-3 acceptance must also assert user/model-visible failed, the reason, and a retry entry point.
- **Repeated ledger sections**: automatic returned at `:5347` and manually supplemented returned at `:5462` are append-only corrections/projection history, not duplicate delivery of the same report. What actually needs fixing is that subsequent artifacts/decisions are silently short-circuited by `dispatch-store.ts:282-289` when the domain is already returned, and that projections cannot be replayed.
- **P1-4 historical recursive filenames**: the current file’s existence proves historical contamination, not that the current entry point still generates them. The original report already qualifies this; keep it as a historical-data issue and do not upgrade it to a current-routing P0.
- **Test records**: the `nodetest` log supports dispatch 15/15 and superagent 83/83; `vitest-dispatch.log:8-10` actually says “No test files found, exit 1,” so that channel cannot be counted as passing.
- **Source comments contradict the implementation**: `dispatch-reports.ts:11-12` claims projection occurs after delivered, while `superagent.ts:3923-3950` actually projects before deliver/settle; `superagent.test.ts:883` also has a contradictory comment. The report correctly cites the implementation order, but comment/test semantic drift should be included in repair acceptance.
- **Memory §4.8 documentation drift**: a subtask already established that the Chinese README statement in the existing goal document is outdated; the Windows report continues to list “memory §4.8” as current drift without rechecking the owner. Withdraw this item or change it to “an outdated statement in the goal assessment itself.”

### 5.3 Unsupported stronger conclusions

The current evidence does not support “26 duplicate reports have occurred live,” “every normal reporting loop is reliable,” “the domain is currently not open,” “the current ACLs were definitely written by this boot,” “Deny DeleteChild does not take effect for any deletion,” “EPERM did not exist at all this round,” “empty output is equivalent to turn execution failure,” or “default memory search is only P2.” These should be handled respectively as factual errors, insufficient evidence, excessive conclusions, or overly broad wording, rather than uniformly reducing the credibility of the entire evaluation.

## 6. Recommended final rating and next steps

### 6.1 Final rating

**Retain C+; no P0 is closed. Retain all four original P0 findings with no downgrades.** Normal reporting and current domain writes are real progress, sufficient to refute both “Windows reports simply cannot come back” and “the domain is currently disabled”; however, duplicate claims, incorrect business termination, unrecoverable delivery, and broken identity across abort still prevent the B-level judgment of “reliable loop closure.” Withdrawing the incorrect domain P1-1 does not offset these core problems.

The recommended final issue classification is: P0-1 through P0-4; P1 includes default memory search, investigation of current persistent ACL/Low side effects, the esbuild/build permission failure, partial start failure, projection correction, and authority consistency; domain data-source observability can be P2, and single sampling should be listed only as a static lifecycle risk.

### 6.3 Review method and limits

This review read the original report, handoff, and all three evaluation scales in full; it checked the runtime’s `dispatch-reports.ts`, `superagent.ts`, `dispatch-store.ts`, related tests, profile/base storage routes, live Inspect, journal, Markdown, raw zstd logs for super/child Sessions, SQLite, and read-only ACLs. It did not restart 3080, inject real delivery failures, trigger abort, change ACLs, or open a UI requiring credentials, so these items remain static or unverified.

The original 26/6 figures have no raw logs from which to recompute them; the independent rerun did not complete because of execution-environment restrictions and cannot be recorded as either passing or reproducing the result. The current journal/SQLite will continue to grow. This review used same-day task ids and timestamps to distinguish the original cutoff from subsequent state, and did not treat the later 12 delivered as the original report’s 10 delivered at that time.
