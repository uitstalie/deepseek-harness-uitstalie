## What changed

- Safe autofixes and their directly exposed repairs removed 100 errors, including the necessary `Block` assertions that the fixer had removed incorrectly.
- A source-only pass removed 31 errors: four intentional promise handlings and 27 redundant string conversions.
- The test pass inserted `void` before 1,048 `no-floating-promises` expressions in 63 test files, and touched no source file.
- Four reviewed source groups removed the remaining 53 safe findings in store-atom, persona-card, jira-core with jira-cli, and jira-agent with the UI.
- Two line-scoped `require-await` suppressions cover `ToolDefinition.execute` methods whose interface requires a Promise; removing `async` would change the return contract.

## Why the remaining findings stay

The 541 test findings describe test registration and fixture shapes rather than shipped behavior. Rewriting them mechanically would create a much larger diff than the risk justifies, so they remain as a known noise floor.

The 22 source `no-unnecessary-condition` findings are runtime defenses at trust boundaries, including persisted JSON, model arguments, and platform timers. Removing a check to make the linter green would trade a real defensive path for an artificial result.

The two contract suppressions are intentional: an `execute` method that must return a Promise cannot drop `async` without changing the ToolDefinition interface.

## Known traps

Do not run a repository-wide `lint:fix` again. Its safe-fix mode can remove a type assertion that is actually necessary, and its void cleanup can turn a deliberate suppression into an unused expression.

`no-floating-promises` and `no-meaningless-void-operator` conflict on test registrations in this repository. Fix test promises through a rule-scoped pass or an exact insertion tool, then rerun the full lint to prove that no new `no-meaningless-void-operator` finding appeared.

## Open contract work

The memory summary still reads `snapshotEvents`, which is deprecated; it needs a migration to the replacement API before the `no-deprecated` finding can be removed.

The exported generic in `serviceOf<T>` is used once; removing it would change the callable signature and needs an API decision rather than a lint edit.
