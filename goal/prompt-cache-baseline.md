# Token 与缓存基准（2026-10-26）

记录这张基准表的用途：任何新增 prompt / 工具描述 / 注入段，都要能解释它对下列数字的影响；**目标是不让静态插入改变缓存命中率，也不让动态写入频繁打断前缀**。

## 基准数值

来源：Web 用量视图，日期 2026-10-26。

| 项 | Token | 占总量 | 占输入 |
|---|---:|---:|---:|
| 总用量 | 741,704,925 | 100% | — |
| 输入（命中缓存） | 730,120,576 | 98.43% | 98.69% |
| 输入（未命中缓存） | 9,724,439 | 1.31% | 1.31% |
| 输出 | 1,859,910 | 0.25% | — |

- 输入合计 = 命中 + 未命中 = 739,845,015。
- 缓存命中率（按输入）= 98.69%；输出/输入 = 0.25%。

## 口径

- **静态插入**（工具 schema、system prompt 段、说明文字）：只在会话第一次请求改变前缀，之后应全部命中。可接受的代价是每次请求多出的输入 token（缓存价）。
- **动态写入**（PERSONALITY.md 条目、memory 快照等）：写入后下一次请求从被改动的段起失效。应尽量低频、可预期。
- 对比时用**同日同请求量**：命中率不应下降，未命中增量应接近“静态插入字节数 × 新会话数 + 动态写入次数 × 受影响前缀长度”。

## 2026-10-27 的插入点（DH-9 / DH-302）

| 插入 | 模型可见 | 体积 | 影响 |
|---|---|---|---|
| `personality_propose` 工具定义 | 是（请求 tools 列表） | 1,173 字符（`description` + `parameters` + `output.schema` 的 JSON 长度） | 静态；每请求多约 300–400 token，首次请求后命中缓存 |
| `ui-personality` 设置页、`remote.personality`、`settings.sectionId` | 否 | — | host/UI 元数据，0 prompt token |
| turn-end 自动学习 | 间接 | 每条正文 ≤ 512 字节/会话，默认最多 3 条 | 写入后 PERSONALITY 段变化，下一次请求从该段起失效；每次会话最多 3 次 |

参考：同包 `personality_learn` 的定义为 1,232 字符（既有，非本次新增）。

## 需要时的收紧手段

- 把 `personality.autoLearn.entries` 设为 `0` 可关闭 turn-end 自动写入，personality 段只在用户编辑或接受 identity 提案时变化。
- 新增 prompt 一律走静态内容；不要在同一次会话里反复改写已注册的 system prompt 段。
- 若以后加“按请求变化”的描述，先对照本表估算未命中增量。
